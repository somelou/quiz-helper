# 已保存密钥显示的系统级鉴权设计

## 1. 背景

当前 `quiz-helper` 的大模型配置与联网搜索配置都允许用户在设置页抽屉中直接点击“显示”按钮，把已保存的 `API Key` 从密码态切换为明文态。

现状问题：

- 已保存密钥的显示没有任何二次校验。
- 只要能打开设置页，就能直接看到本地保存的敏感密钥。
- “新增时可直接输入”和“已保存后再查看”这两种场景没有被区别对待。

本次设计的目标，是在不改变现有存储结构和主流程的前提下，为“查看已保存密钥”增加系统级鉴权门槛。

## 2. 目标

- 仅对“查看已保存且未修改的密钥”增加系统级鉴权。
- 优先使用 `WebAuthn`，由浏览器调起系统级验证能力，例如 `Touch ID`、`Windows Hello` 或安全密钥。
- 在当前 `options` 页内，一次验证成功后，本页范围内所有已保存密钥都允许显示。
- 页面刷新、关闭或扩展重载后，解锁状态立即失效。
- 浏览器或系统不支持时，不做降级方案，不允许显示已保存密钥。
- 对新增密钥和主动修改中的密钥保持顺手的编辑体验，不额外增加阻力。

## 3. 非目标

- 不改动密钥当前的本地存储位置，仍保存在 `chrome.storage.local`。
- 不实现插件内 `PIN`、口令或其它降级鉴权方式。
- 不提供“手动重新锁定”按钮。
- 不提供跨页面、跨标签页或跨浏览器窗口共享的解锁状态。
- 不实现“复制已保存密钥前再鉴权”的独立能力，本次仅处理显示控制。
- 不调整大模型或搜索服务商的数据结构，只在界面层补充鉴权判断。

## 4. 适用范围

本设计仅覆盖设置页中的两类敏感字段：

- `options/model-section.js` 中的大模型 `API Key`
- `options/search-section.js` 中的搜索服务商 `API Key`

不扩展到其它字段，也不影响后台请求实际读取密钥的能力。

## 5. 核心方案

### 5.1 总体策略

采用“当前设置页全局解锁”的策略：

- 当用户在当前 `options` 页第一次尝试显示已保存密钥时，先触发一次 `WebAuthn` 系统级鉴权。
- 鉴权成功后，将本页内存态标记为“已解锁”。
- 在当前页面生命周期内，本页中所有“已保存且未修改”的密钥字段都可以正常切换显示/隐藏。
- 一旦页面刷新、关闭或扩展被重载，本页内存态消失，自动重新回到锁定状态。

### 5.2 场景区分

需要严格区分以下三种情况：

1. 新增密钥
   - 当前记录原本没有已保存密钥。
   - 用户正在输入新值。
   - 此时“显示/隐藏”按钮不需要系统鉴权，可直接切换。

2. 主动修改密钥
   - 当前记录原本已有已保存密钥。
   - 用户已对输入框内容产生修改。
   - 此时展示的是“当前输入中的新值”，不再属于“查看已保存密钥”场景，可直接切换。

3. 查看已保存且未修改的密钥
   - 当前记录原本已有已保存密钥。
   - 用户未修改输入框内容。
   - 此时属于受保护场景，若当前页面未解锁，则必须先完成 `WebAuthn` 鉴权。

### 5.3 页面级解锁状态

页面解锁状态只存在于当前 `options` 页内存中，不写入持久化存储。

建议维护以下运行态：

- `isOptionsKeyViewUnlocked`
- `optionsKeyViewUnlockedAt`
- `isWebAuthnSupported`
- `isWebAuthnConfigured`

其中：

- `isOptionsKeyViewUnlocked` 决定本页是否已解锁。
- `optionsKeyViewUnlockedAt` 仅用于调试和界面提示，不参与持久化。
- `isWebAuthnSupported` 表示浏览器与当前上下文是否支持 `WebAuthn`。
- `isWebAuthnConfigured` 表示用户是否已经在本扩展内完成过一次凭证注册。

## 6. WebAuthn 方案设计

### 6.1 注册阶段

用户需要先在设置页启用系统级鉴权，完成一次本地凭证注册。

注册阶段流程：

1. 用户进入设置页的“系统级鉴权”区域。
2. 点击“启用系统级鉴权”。
3. 页面调用 `navigator.credentials.create()` 创建 `publicKey` 凭证。
4. 浏览器调起系统级验证界面。
5. 成功后，仅保存用于后续校验所需的最小元数据。

由于本场景不依赖后端服务，注册后的数据只用于本地“是否拥有可用于验证的凭证”判断与本地校验流程。

### 6.2 验证阶段

当用户点击受保护字段的“显示”按钮时：

1. 若当前页面已解锁，则直接切换显示。
2. 若当前页面未解锁，则发起 `navigator.credentials.get()`。
3. 浏览器调起系统级验证。
4. 验证成功后，将本页标记为已解锁。
5. 当前字段显示明文；本页其它已保存密钥也可继续显示。

### 6.3 不支持与未配置的处理

需要区分两个状态：

- 环境不支持 `WebAuthn`
- 环境支持，但用户尚未完成本扩展的系统鉴权注册

两者的统一结果都是：

- 已保存密钥不可显示。
- “显示”按钮置为禁用态。
- 按钮或提示文案统一为：`无法显示已保存密钥`

其中“未配置”不额外提供本字段内的临时降级入口，而是引导用户先到设置页的系统级鉴权区域完成启用。

## 7. UI 设计

### 7.1 设置页新增区域

在 `options/options.html` 的基本设置卡片中新增“系统级鉴权”配置区，建议放在通用设置区域中，避免散落到每个抽屉里重复配置。

建议结构：

- 标题：`系统级鉴权`
- 状态文案：
  - `未启用`
  - `已启用`
  - `当前环境不支持`
- 主按钮：
  - 支持且未启用时：`启用系统级鉴权`
  - 支持且已启用时：`重新注册`
- 辅助说明：
  - 用于控制“已保存 API Key”的显示权限
  - 仅在当前设置页生命周期内保持解锁
  - 刷新或关闭页面后需重新验证

### 7.2 抽屉中的按钮状态

`API Key` 输入框右侧现有“显示/隐藏”按钮保持不变，但状态逻辑调整如下：

1. 新增记录
   - 按钮可点击
   - 正常 `显示 / 隐藏`

2. 已存在记录，且用户已修改输入值
   - 按钮可点击
   - 正常 `显示 / 隐藏`

3. 已存在记录，且当前值仍是已保存原值
   - 若本页已解锁：按钮可点击，正常 `显示 / 隐藏`
   - 若本页未解锁：点击先触发系统级鉴权

4. 当前环境不支持，或尚未启用系统级鉴权
   - 按钮禁用
   - 提示：`无法显示已保存密钥`

### 7.3 提示文案

推荐的最小文案集合：

- 设置区说明：`用于控制已保存 API Key 的显示权限`
- 支持但未启用：`启用后，查看已保存密钥时将触发系统级验证`
- 已启用：`当前页首次查看已保存密钥时，需要进行一次系统级验证`
- 不支持：`当前环境不支持系统级鉴权，无法显示已保存密钥`
- 按钮禁用提示：`无法显示已保存密钥`

## 8. 数据设计

### 8.1 持久化字段

建议新增以下本地存储字段：

- `webauthn_key_view_enabled`
- `webauthn_key_view_credential_id`
- `webauthn_key_view_label`
- `webauthn_key_view_created_at`

说明：

- `webauthn_key_view_enabled` 表示是否已启用此能力。
- `webauthn_key_view_credential_id` 用于后续本地校验定位凭证。
- `webauthn_key_view_label` 仅用于界面友好展示，可选。
- `webauthn_key_view_created_at` 用于状态展示或后续迁移。

### 8.2 非持久化页面态

以下状态仅保存在 `options` 页内存：

- `isOptionsKeyViewUnlocked`
- `optionsKeyViewUnlockedAt`
- `isWebAuthnSupported`
- `isWebAuthnConfigured`

页面销毁时自动丢失，不额外清理存储。

## 9. 模块划分

### 9.1 新增共享模块

建议新增共享模块，例如：

- `shared/webauthn-key-visibility.js`

职责：

- 能力检测
- 凭证注册
- 本地校验入口
- 当前页面解锁状态管理
- 为 `options` 页提供统一接口

建议暴露的接口形态：

- `detectSupport()`
- `loadConfig()`
- `registerCredential()`
- `ensureUnlocked()`
- `isUnlocked()`
- `isConfigured()`
- `canRevealSavedSecret()`

### 9.2 设置页协调层接入

`options/index.js` 负责：

- 初始化系统级鉴权模块
- 渲染基础状态
- 把统一的“是否允许显示已保存密钥”能力传给模型与搜索模块

### 9.3 模型模块接入

`options/model-section.js` 需要补充：

- 记录抽屉打开时的原始 `apiKey`
- 判断当前输入是否已被用户修改
- 在“显示”按钮点击时调用统一鉴权入口
- 根据支持状态与配置状态设置按钮禁用态和提示文案

### 9.4 搜索模块接入

`options/search-section.js` 需要补充：

- 记录抽屉打开时的原始 `apiKey`
- 判断当前输入是否已被用户修改
- 在“显示”按钮点击时调用统一鉴权入口
- 根据支持状态与配置状态设置按钮禁用态和提示文案

## 10. 行为流程

### 10.1 首次启用系统级鉴权

1. 用户打开设置页。
2. 页面检测 `WebAuthn` 能力。
3. 若支持，则在基本设置卡片显示“启用系统级鉴权”入口。
4. 用户点击启用。
5. 浏览器弹出系统级验证界面。
6. 注册成功后，本地保存最小配置。
7. 页面显示“已启用”状态。

### 10.2 未解锁时查看已保存密钥

1. 用户打开模型或搜索配置抽屉。
2. 当前记录已有已保存密钥，且输入框值未被修改。
3. 用户点击“显示”。
4. 若当前页面未解锁，则调用 `ensureUnlocked()`。
5. 浏览器触发系统级验证。
6. 验证成功后，本页标记为已解锁。
7. 输入框切为明文态。

### 10.3 已解锁后查看其它已保存密钥

1. 当前 `options` 页已完成一次系统级验证。
2. 用户切换到另一个模型或搜索服务商抽屉。
3. 点击“显示”时，不再重复触发系统验证。
4. 直接切换为明文态。

### 10.4 解锁失效

以下任一情况发生时，页面级解锁态自动失效：

- 刷新设置页
- 关闭设置页
- 扩展重载

由于解锁态不持久化，这些场景不需要额外写回锁定状态。

## 11. 错误处理

### 11.1 用户取消系统验证

- 不显示报错弹窗轰炸。
- 当前字段保持隐藏态。
- 可在抽屉内轻量提示：`未完成系统验证，已保存密钥仍保持隐藏`

### 11.2 浏览器不支持

- 按钮禁用。
- 统一提示：`无法显示已保存密钥`

### 11.3 已启用但凭证异常

例如：

- 本地配置存在，但系统凭证不可用
- 凭证被系统删除
- `navigator.credentials.get()` 抛异常

处理策略：

- 当前字段保持隐藏。
- 设置页系统级鉴权区域提示：`系统级鉴权状态异常，请重新注册`
- 用户可通过“重新注册”恢复。

## 12. 安全边界与风险

### 12.1 本次增强解决的问题

- 阻止无门槛直接查看已保存密钥
- 将“查看已保存密钥”与“正在输入或修改密钥”区分开
- 避免把解锁状态带出当前页面生命周期

### 12.2 本次增强不解决的问题

- 本地存储中的密钥本身仍是明文可读的浏览器扩展数据
- 拥有本机高权限访问的人仍可能通过其它方式读取扩展存储
- 后台实际使用密钥时不会再次经过本设计的显示鉴权逻辑

因此，本设计提升的是“设置页显示层”的访问门槛，而不是将本地存储升级为操作系统级密钥保管。

## 13. 测试策略

建议覆盖以下测试场景：

- 支持 `WebAuthn` 且已启用时，首次显示已保存模型密钥会触发系统验证
- 支持 `WebAuthn` 且已启用时，首次显示已保存搜索密钥会触发系统验证
- 在同一设置页中，首次验证成功后，第二个已保存密钥可直接显示
- 新增模型时，未保存前的密钥可直接显示
- 编辑已有模型时，修改后的当前输入值可直接显示
- 浏览器不支持时，按钮为禁用态，提示为 `无法显示已保存密钥`
- 刷新设置页后重新回到锁定状态
- 关闭设置页后重新打开，重新回到锁定状态
- 扩展重载后重新回到锁定状态
- 用户取消系统验证后，字段仍保持隐藏
- 凭证异常时，显示入口不可放行，并给出重新注册提示

## 14. 实施建议

建议按以下顺序实现：

1. 新增 `WebAuthn` 共享模块，先完成能力检测、注册和页面级解锁状态维护
2. 在 `options/options.html` 与 `options/index.js` 中接入系统级鉴权设置区
3. 改造 `options/model-section.js` 的“显示已保存密钥”逻辑
4. 改造 `options/search-section.js` 的“显示已保存密钥”逻辑
5. 补充按钮禁用态和提示样式
6. 完成手工验证与必要的诊断检查

## 15. 决策结论

本次设计最终采用以下规则：

- 方案采用：`当前设置页全局解锁`
- 鉴权方式：`纯系统级优先，仅使用 WebAuthn`
- 不支持时：`不允许显示，按钮禁用，提示“无法显示已保存密钥”`
- 失效时机：`刷新设置页`、`关闭设置页`、`扩展重载`
- 不提供：`PIN 降级`、`手动重新锁定`、`持久化解锁`

该方案在现有项目结构下改动集中、边界明确，能够在不破坏现有配置编辑体验的前提下，为“查看已保存密钥”补上必要的系统级鉴权门槛。
